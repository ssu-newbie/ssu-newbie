# 세피리아 소스 이관과 실행 검증

Claude 인수인계에 이어 LobbyScaling 9.6.0과 DamageMeter 1.1.1의 실제 소스를 확보했다. 두 파일은 버전 선언·패치 경로를 대조하고 클래스별 파일로 분리했다. 빌드·게임 실행 확인은 아직 남아 있다.

## 확보한 소스와 추가 수집 대상

`LobbyScaling_9.6.0.cs`와 `DamageMeter_1.1.1.cs`는 확보했다. 원본 SHA-256과 검토 결과는 [소스 대조 문서](sephiria-source-audit.md)에 있다. 아래 나머지 모드는 `.cs` 또는 ZIP의 `Plugin.cs.txt`가 필요하다.

| 모드 | 인수인계에 기록된 소스 | 확인할 버전 |
| --- | --- | --- |
| Lobby Scaling | `LobbyScaling_9.6.0.cs` | 9.6.0 |
| Damage Meter | `DamageMeter_1.1.1.cs` | 1.1.1 |
| Chat Macro | `ChatMacro_1.5.0.cs` | 소스 1.5.0 → 재컴파일본 1.5.2 기록 |
| Config Panel | `ConfigPanel_1.1.0.cs` | 소스 1.1.0 → 재컴파일본 1.1.1 기록 |
| AddOn Bridge | `AddOnBridge.cs` | 1.0.0 |
| Stage Probe | `StageProbe.cs` | 1.0.0 |
| Probe | `Probe_2.0.0.cs` | 2.0.0 |

파일명으로 버전을 확정하지 않는다. 수집 후 파일 해시, 코드의 플러그인 버전, 참조 어셈블리, 실제 로드 로그를 대조한다. 모드 ZIP과 별도 `.cs`가 모두 있다면 같은 내용인지 확인하고 원본 둘 다 보존한 뒤 기준본을 정한다.

## 받을 자료와 공개 저장소의 구분

- 우선 필요한 자료: 작성한 모드 소스, 기존 빌드 명령·설명서, 문제 발생 시점의 로그.
- 실행 검증에 필요한 정보: 게임·Unity·BepInEx 버전, 설치한 모드와 버전, 플레이 인원, 호스트 여부, 해당 설정값.
- 원본 로그는 검토 후 관련 구간만 문서에 남긴다. 사용자 경로, 친구 이름, 채팅 내용은 공개 기록에서 제외한다.
- 게임 DLL, 타사 모드 통합팩, 개인 채팅 매크로 설정은 공개 저장소에 포함하지 않는다. 빌드 참조는 사용자의 게임 설치 폴더에서 가져오는 방식으로 구성한다.

## 소스를 받은 뒤 수행할 작업

1. 원본 파일 목록과 SHA-256을 기록한다. 과거 날짜의 커밋 이력은 만들지 않는다.
2. 실제 소스에서 플러그인 GUID·버전·의존성·패치 대상·설정 키를 추출한다.
3. 모드별 소스 폴더와 빌드 설정을 만든다. 대상 프레임워크와 참조 목록은 확보한 소스와 실제 게임 어셈블리에 맞춰 결정한다.
4. 컴파일용 대역 DLL 대신 실제 게임 참조로 빌드한다. 빌드 성공과 실행 성공을 별도로 기록한다.
5. 사용자가 실제 게임에서 아래 항목을 실행하고, 결과 로그를 받아 통과 여부를 판단한다.

## 실제 게임 검증 표

각 비교에서는 게임 버전, 활성 모드 목록과 설정, 난이도, 스테이지, 인원 수를 기록한다. 적용 전후를 비교하는 항목은 비교 대상 외 조건을 가능한 한 동일하게 유지한다.

| 항목 | 실행 절차 | 완료 판단에 필요한 근거 |
| --- | --- | --- |
| 플러그인 로드 | 모드별로 시작한 뒤 함께 로드 | 로그의 GUID·버전 일치, 관련 로드 예외 없음 |
| 파티 인원과 스폰 수 | 2·3·5인 조건의 계산값과 스폰 결과 기록 | 입력 인원, 원본 배율, 수정 배율, 실제 결과 연결. 플레이를 못 한 인원 조건은 정적 분석으로 구분 |
| UI 표시 | Damage Meter·Chat Macro·Config Panel 표시·숨김 실행 | UI 스크린샷 및 해당 구간 로그. `MissingFieldException` 재발 여부 확인 |
| 스포너별 능력치 | 서로 다른 스포너가 나오는 스테이지 진행 | 각 스포너 타입의 적용 로그와 다음 스테이지에도 패치가 유지되는 근거 |
| 보스 체력 | 기준 설정과 수정 설정으로 각각 실행 | 실제 유닛 체력의 적용 전·후 값. 스포너 필드 변경 로그만으로 완료 처리하지 않음 |
| Config Panel Apply | 기존 cfg를 백업한 뒤 대표 설정 하나 변경 | 화면 값, 실행 중 효과, 재시작 후 값의 일치 여부를 각각 기록 |
| Damage Meter | 고정 대상에게 피해를 주고 표시 비교 | 기존 게임 통계와 UI 수치 대조. 새 네트워크 구현 성과로 표현하지 않음 |

## 사례별 기록 양식

| 필드 | 작성할 내용 |
| --- | --- |
| 환경 | 게임·Unity·BepInEx·모드 버전, 호스트/클라이언트, 인원 수 |
| 재현 | 설정값과 실행 순서, 기대 결과 |
| 관찰 | 실제 결과와 관련 원본 로그 구간 |
| 원인 | 해당 소스 위치·패치 시점·참조 타입과 관찰의 연결 |
| 변경 | 수정한 파일과 커밋, 변경 이유 |
| 검증 | 동일 조건의 재실행 결과, 남은 한계 |
| 상태 | 인수인계 기록 / 소스 대조 / 빌드 확인 / 실행 확인 |

우선 사례는 Rect 멤버 종류 불일치, Harmony Postfix 적용 시점, 타입별 FieldInfo 캐시다. 로그나 수정 전 코드가 없으면 인수인계에 기록된 사례로 남기고 과거 근거를 재구성하지 않는다.

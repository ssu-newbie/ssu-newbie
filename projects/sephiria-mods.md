# 세피리아 모드 제작

> 원하는 플레이 경험을 정의하고, 내부 동작 분석과 재현 실험으로 구현 방향을 검증한 프로젝트입니다.

이 문서는 이전 Claude 작업의 인수인계와 사용자 경험 기록을 정리한 초안입니다. 아래 구현·디버깅 내용은 해당 기록에 근거하며, 최신 소스와 원본 실행 로그의 파일 단위 대조는 남아 있습니다.

| 항목 | 내용 |
| --- | --- |
| 대상 | Unity 기반 로그라이크 게임 「세피리아」 |
| 작업 | 모드 요구사항·밸런스 설계, AI 협업 구현, 실제 게임 검증 |
| 주요 기술 | C#, .NET / Mono, BepInEx, HarmonyX, Mono.Cecil |
| 협업 방식 | Claude의 코드 작성·정적 분석과 사용자의 요구사항 정의·실행·로그 수집 |

## 접근 방식

게임의 원본 소스가 공개되지 않은 환경에서 모드를 제작했습니다.
먼저 원하는 동작과 변경 범위를 정했습니다. Claude가 수행한 IL 분석과 직접 수집한 실행 로그를 함께 검토하며 관련 구조를 파악했습니다.
이후 구현, 빌드 실행, 로그 수집, 가설 검증을 반복하며 기능과 밸런스를 조정했습니다.

### 사용한 기술과 목적

| 기술 | 사용 목적 |
| --- | --- |

| Mirror | 멀티플레이 동작과 관련된 구조 분석 |

## 문제 분석 사례: 파티 인원과 적 수

### 관찰한 현상

파티 인원이 3명 이상일 때 적 수가 인원 증가에 따라 달라지지 않고 고정되는 현상을 확인했습니다.
이 사례에서는 인원별 결과를 비교할 수 있는 재현 조건을 만드는 것이 먼저였습니다.

### 분석과 판단

인원 수를 처리하는 조건 분기를 살펴보고, 분기의 우선순위 때문에 의도한 계산에 도달하지 못하는 문제를 분석했습니다.
관찰한 현상과 코드의 조건을 연결해 수정 방향을 제안했습니다.

### 이 경험에서 남긴 것

- 현상을 설명할 수 있는 재현 조건을 먼저 확보하는 습관
- 개별 조건의 내용과 함께 평가 순서를 확인하는 디버깅 관점
- 생성된 코드나 설명을 실행 로그로 다시 확인하는 검증 과정

## 맡은 역할

- 추가할 기능과 밸런스의 요구사항 정의
- 빌드 실행과 로그 수집
- 관찰 결과에 따른 가설 수립과 검증
- AI가 작성한 모드의 실제 게임 검증과 최종 판단

Claude는 C# 코드 작성과 어셈블리 분석을 담당했고, 무엇을 바꿀지와 실제로 어떻게 동작하는지는 직접 요구사항과 플레이 검증으로 확인했습니다.
기능을 만드는 과정과 함께, 그 기능이 의도대로 동작하는지 설명할 수 있는 근거를 남기는 경험을 쌓았습니다.

## 추가로 정리할 디버깅 사례

### UI 함수 첫 줄의 로그도 나오지 않던 문제

인수인계에는 `UnityEngine.Rect`의 프로퍼티를 컴파일용 대역 DLL에서 필드로 선언해 `MissingFieldException`이 발생한 사례가 기록되어 있습니다. UI 배치만 고쳐서는 해결되지 않아, 실제 예외와 참조 어셈블리의 차이를 추적했습니다. 후속 빌드는 사용자가 가진 게임의 실제 참조 DLL로 구성하고, 수정 전후 소스와 로그를 연결할 예정입니다.

### 보스 체력 로그는 바뀌지만 실제 체력은 바뀌지 않던 문제

기록된 원인은 `BossSpawner.OnStartServer`가 필드를 이미 읽은 뒤 Harmony Postfix가 값을 변경한 것이었습니다. 유닛에 직접 적용하는 경로로 수정했지만 실제 보스 체력의 변경을 입증하는 후속 로그는 확보되지 않았습니다. 포트폴리오에서는 원인 분석·수정 방향과 최종 실행 검증을 구분합니다.

### 한 타입의 캐시 오류가 모든 패치를 멈추던 문제

서로 다른 스포너에 같은 `FieldInfo` 캐시를 사용해 예외가 났고, 전역 실패 플래그 때문에 이후 패치까지 중단된 사례입니다. 인수인계에는 타입별 캐시와 실패 범위 축소로 변경했다고 기록되어 있습니다. 해당 변경 전후 코드와 스테이지별 로그를 확보해 재현 과정으로 정리할 예정입니다.

## 소스 이관 순서

1. 최신 `.cs` 또는 직접 작성한 모드 ZIP의 `Plugin.cs.txt`를 수집하고 파일명·플러그인 버전·출처를 기록합니다.
2. 기존 날짜의 Git 이력을 재구성하지 않고, 확보한 원본을 기준 커밋으로 남깁니다.
3. 모드별 소스 폴더와 빌드 설정을 만들고, 게임 DLL은 로컬 참조로 관리합니다. 상용 게임 DLL·타사 통합팩·개인 채팅 설정은 저장소에 넣지 않습니다.
4. 대표 사례의 환경, 재현 절차, 기대 결과, 실제 로그를 문서화합니다.
5. 보스 체력·Config Panel Apply 등 미검증 기능은 실행 결과를 확보한 뒤 완료로 표시합니다.

## 정리 상태

현재 문서는 전달된 인수인계와 경험 기록을 바탕으로 작성했습니다. 모드 소스와 원본 로그를 받아 파일 단위 근거를 연결하는 작업이 남아 있습니다. 공개 배포 여부와 다운로드 수치는 자료 간 기록 범위가 일치하는지 확인 중이므로 성과로 기재하지 않습니다.
